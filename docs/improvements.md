# 项目完善与知识组织

本次代码审查发现：已有来源快照、人工审核、事实版本与检索审计链路；接下来应优先提高知识覆盖率与录入效率。

## 本次落地

- 界面采用奶油白、蔷薇粉、香槟金描边和拱形徽章；标题改用清晰的微软雅黑粗体，增大正文并提高对比度。知识浏览桌面四列，提供回到顶部按钮与 Alt + ↑ 快捷键。
- 首页改为方案对话，用户自行配置模型 API，Agent 从后台已发布知识生成带引用的方案。20 个开源与开放权重模型已并入知识总览及知识浏览分类树，实体详情提供下载入口与许可证说明。
- 分类细分为领域、能力方向、具体任务三级。模型覆盖语言、视觉、音频、视频、多模态、嵌入与排序；框架覆盖 Agent、RAG、训练、评测。
- 八类实体分别提供字段建议，提交事实时可以点选字段；字段只是录入提示，事实依然需要原文证据与审核。
- 分类补全可重复执行，只增加缺少的分类，不移动已有实体，不覆盖已发布事实。新建演示库也使用细分类目。

## 给已有数据库补全分类

在项目 backend 目录的 PowerShell 中，使用可用的 Python 环境执行：

```powershell
py -m app.taxonomy
```

API 与命令必须使用同一个 DATABASE_URL。默认库为当前 backend 目录的 knowledge.db。分类增补后，在页面点击刷新。现有实体继续保留原有分类，可在编辑实体时人工细分。

## 知识录入规则

1. 将厂商、产品、具体模型版本、API 服务分别建为实体，建立“开发模型”“旗下产品”“提供接口”“依赖组件”等有方向的关系。
2. 描述说明用途；参数、计费、许可证、部署条件分别作为事实保存，不把整篇文档塞进一个字段。
3. 价格需注明币种、输入或输出、计费单位、地区与生效时间；性能结果需注明数据集、评估方法与运行条件。
4. 同一字段在同一实体上保持统一名称。版本差异较大时分别建模，再建立版本关系。
5. 优先使用官方文档，证据与原文快照绑定。暂缺资料的维度留空；演示内容继续保留演示标记。

## 后续优先级

| 优先级 | 缺口 | 建议验收方式 |
| --- | --- | --- |
| P1 | 真实条目的参数深度仍不足 | 在现有 116 个真实条目基础上补充版本化参数、部署要求和有日期的价格事实 |
| P1 | 总览缺少知识质量提示 | 展示无来源实体、无事实实体、超期未检查来源，点击可筛选 |
| P1 | 事实字段依赖人工统一 | 将前端建议字段升级为后端字段规范，明确单位、类型与别名 |
| P1 | 分类不能折叠、实体较多时浏览成本高 | 分类树支持展开折叠、列表分页，保留筛选条件 |
| P2 | 当前检索为关键词匹配 | 先建立固定查询与预期证据集，再评估中文分词、混合检索的命中质量 |
| P2 | 普通网页需要人工整理事实 | 增加切片和抽取候选，候选必须经过现有证据检查与审核 |
| P2 | 运营处理依赖逐条操作 | 批量录入预检、重复实体提示、失败重试与质量报表 |
| P3 | 尚无面向团队的权限模型 | 扩展用户、角色、审核责任人与审计权限后再支持团队协作 |
